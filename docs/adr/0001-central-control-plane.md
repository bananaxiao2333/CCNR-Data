# 0001. CCNR-Data 升级为中枢控制面

- 状态：已接受
- 日期：2026-10-24
- 相关：[docs/06](../06-控制面与统计.md)、[docs/02](../02-协议契约.md)

## 背景

现状是「数据在 CCNR-Data，身份在 Casdoor，准入散落在代理配置，统计靠日志」：

- bot 要查服务器信息，原方案打算直连 KubeMCGate，但 KubeMCGate 的接口与部署都未定；
- Velocity 需要按账号状态放行/拒绝，但没有任何统一入口回答「这个玩家能不能进」；
- 会话、在线、时长、登录失败没有落库，排障只能翻代理日志；
- 模组侧已经把事件与结算上报到 CCNR-Data，但身份、代理、统计三条线各自为政。

如果每个消费者各接一套（bot 接 KubeMCGate、代理接 Casdoor、统计接日志），会出现三套
「在线」「封禁」口径，和等级曲线算三遍是同一类问题。

## 决策

1. CCNR-Data 从「模组数据存储」升级为**中枢**：统一身份投影、准入决策、会话统计、查询。
2. 新增 `control.v1.ControlService`，与既有 `moddata.v1.ModDataService` 同进程注册；
   **`moddata.v1` 冻结**，模组侧零改动。
3. 业务面只用 gRPC；HTTP 仅保留健康、Prometheus 指标、身份回调三个边缘端点。
4. Casdoor 仍是唯一身份源；CCNR-Data 只存 `player_identities` 投影，不读 Casdoor 库。
5. `server_id` 就取 Velocity 的服务器名；**本期不接 KubeMCGate**。
6. 保持既有故障隔离：CCNR-Data 不调用 Gate 做连接/转服/踢人，游戏动作由代理或模组执行。
7. 准入失败默认拒绝（fail-closed），插件用缓存与超时保证在线玩家不受影响。

## 后果

### 正面

- 身份、准入、统计只有一个口径；bot 与代理都读同一份数据；
- 模组契约稳定，升级风险被隔离在新包内；
- 代理侧逻辑变薄：本地只做缓存、队列、把决策翻译成 kick 消息。

### 负面 / 代价

- CCNR-Data 从「只写不读外部」变成依赖 Casdoor 可用性；用缓存 + 熔断 + fail mode 兜底；
- 控制面与数据面同进程，故障域扩大；用独立线程池、健康检查与限流隔离；
- 需要新增身份桥（皮肤站回调或管理导入），否则准入无法启用。

## 备选方案

| 方案 | 为什么不选 |
| --- | --- |
| bot 直连 KubeMCGate / 代理直连 Casdoor | 两套口径，且把第三方 API 泄漏到消费者 |
| 新建独立 auth 服务 | 多一个进程、多一份数据库，当前规模不划算；控制面本来就是它的前身 |
| 只用代理本地白名单 | 无法复用 Casdoor 的邮箱验证与角色，统计也仍然缺失 |
| 把控制逻辑塞进 `moddata.v1` | 模组契约已上线，语义也被污染 |

## 何时重新评估

- 控制面 QPS 或可用性要求超过单进程能力（需要独立部署 / 多副本）；
- 代理数量增长到需要集中配置分发；
- KubeMCGate 接口稳定，服务器库存需要动态发现。
