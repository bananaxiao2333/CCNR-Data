# 05 · 部署与运维

## 1. 运行

```bash
uv sync
uv run python -m ccnr_data \
  --db-file /var/lib/ccnr-data/ccnr-data.db \
  --bind 0.0.0.0:8081 \
  --event-retention-days 30 \
  --log-level INFO
```

进程内会起三组后台：gRPC 工作线程（`--max-workers`）、日志轮换线程（每小时一轮，启动时先跑一次补上停机期间该清的）、会话收尾线程（每 60 秒把心跳超过 `HEARTBEAT_TTL_S` 的会话标记结束，避免代理崩溃后永远在线）。控制面还会另起一个 HTTP 边缘线程，提供 `/healthz` 与 `/metrics`。

### systemd

```ini
[Unit]
Description=CCNR-Data 统一数据服务
After=network-online.target

[Service]
Type=simple
User=ccnr
WorkingDirectory=/opt/ccnr-data
Environment=CCNR_DATA_DB_FILE=/var/lib/ccnr-data/ccnr-data.db
Environment=CCNR_DATA_BIND=0.0.0.0:8081
ExecStart=/opt/ccnr-data/.venv/bin/python -m ccnr_data
Restart=always
RestartSec=3
# 停机时先 drain 再退：SIGTERM → ServerHandle.stop() 把健康检查置 NOT_SERVING
KillSignal=SIGTERM
TimeoutStopSec=20

[Install]
WantedBy=multi-user.target
```

### 健康检查

标准 gRPC Health Checking Protocol：

```bash
grpcurl -plaintext 127.0.0.1:8081 grpc.health.v1.Health/Check
grpcurl -plaintext 127.0.0.1:8081 grpc.health.v1.Health/Check \
  -d '{"service":"moddata.v1.ModDataService"}'
```

反射是开着的，排障时可以直接 `grpcurl -plaintext 127.0.0.1:8081 list moddata.v1.ModDataService`，不需要把 proto 拷到机器上。

## 2. 备份

SQLite 的唯一正确备份方式是 `.backup`（**不要 `cp`**：运行中的库有 WAL，直接复制会拿到损坏快照）。

```bash
sqlite3 /var/lib/ccnr-data/ccnr-data.db ".backup '/backup/ccnr-$(date +%F-%H%M).db'"
```

- 频率：每小时一次 `.backup`（含 WAL，一致性快照），保留 7 天；每天一次上传异地对象存储。
- 恢复：停服 → 用备份覆盖 → 启动。启动时的模式版本校验会挡住版本不符的库。
- `idempotency` 表**必须一起备份**：丢了它，模组队列里的迟到重放会被当成新请求再执行一次。

## 3. 可观测性

| 信号 | 在哪 |
|---|---|
| 每个写入都有 `audit_log` 行 | `SELECT action, COUNT(*) FROM audit_log GROUP BY action` |
| 变更流积压 | `SELECT MAX(seq) FROM change_log` 与订阅方游标之差 |
| 经验漂移 | WARN 日志「结算前后端经验不一致」+ `settlements.diverged = 1` |
| 轮换执行 | INFO 日志「日志轮换清理：事件 N 行…」 |
| 请求失败 | INFO 日志「<RPC> 拒绝：<原因>（<状态码>）」 |

常用运维查询：

```sql
-- 一天的事件量（判断是否与预期一致）
SELECT COUNT(*) FROM match_events WHERE occurred_at > (strftime('%s','now')*1000 - 86400000);

-- 哪些服务器的结算出现了经验漂移
SELECT server_id, COUNT(*) FROM settlements WHERE diverged = 1 GROUP BY server_id;

-- 每局的事件分布
SELECT match_id, kind, COUNT(*) FROM match_events GROUP BY match_id, kind ORDER BY 3 DESC;
```

**指标（Prometheus）**：控制面在进程内计数，由 HTTP 边缘的 `/metrics` 暴露，不需要额外拦截器。

| 指标 | 类型 | 说明 |
|---|---|---|
| `ccnr_control_authorize_total{decision,reason}` | Counter | 准入决策数与拒绝原因分布 |
| `ccnr_control_authorize_latency_seconds` | Histogram | 准入耗时（含 Casdoor） |
| `ccnr_control_reports_total{kind}` | Counter | 代理事件上报数 |
| `ccnr_control_sessions_online` | Gauge | 最近一次在线查询看到的会话数 |
| `ccnr_casdoor_requests_total{result}` | Counter | Casdoor 请求成功 / 失败 |
| `ccnr_casdoor_circuit_open` | Gauge | 熔断是否打开 |

排障先看 `/healthz`（数据库 / Casdoor 配置），再看拒绝原因分布，最后看 `LOGIN_DENIED` 事件。

## 4. 容量与压测（实测）

```bash
uv run python scripts/loadtest.py                    # 默认 30 人 × 200 条 × 48 局
uv run python scripts/loadtest.py --bench-events 40000 --db-file var/loadtest.db
```

### 4.1 口径

`loadtest.py` 在**本进程内**拉起真实服务（真实 gRPC 回环 + 真实 SQLite），按模组的上报形状打流量：事件种类按真实分布抽样（阶段推进 / 事件触发最频繁），结算按 `SettleSummary` 形状（`gain = Σ lines`），读到 40,000 事件 + 592 结算后再量库增长，并先 `wal_checkpoint(TRUNCATE)` 把 WAL 里的页落盘，避免低估。

### 4.2 延迟（macOS / Apple Silicon，SQLite 3.53.1，16 并发）

| 调用 | 单发 p50 | 单发 p99 | 并发吞吐 | 并发 p99 |
|---|---|---|---|---|
| `GetPlayer` | 0.15 ms | 0.26 ms | 6,261 ops/s | 3.83 ms |
| `RecordEvent` | 0.19 ms | 0.37 ms | 2,221 ops/s | 119 ms |
| `RecordSettlement` | 0.22 ms | 1.03 ms | 1,602 ops/s | 91 ms |
| `ApplyExperience` | — | — | 1,962 ops/s | 115 ms |

**并发 p99 变差是排队，不是变慢**：所有写入串行在 `BEGIN IMMEDIATE` 的写锁上，16 个客户端同时打就会形成队列。真实负载是 3–30 事件/秒（见下），远低于排队阈值——看**单发延迟**才是真实体验。

### 4.3 场景（24 小时不间断 · 30 分钟一局 · 30 人/局 · 200 条日志/人/局）

| 量 | 值 |
|---|---|
| 一局 | 30 × 200 = 6,000 条事件 |
| 一天 | 48 局 → 288,000 条事件 + 1,440 次结算 |
| **一天总行数** | 878,400 行（事件 288k + 变更流 289k + 幂等键 289k + 结算与明细 10k + 审计 1.4k） |
| **实测单行成本** | **233 B/行**（含全部索引） |
| **一天体积** | **≈ 195 MiB** |

### 4.4 会不会膨胀得要死

**不清理的话，会。** 按实测外推：

| 累计 | 体积 |
|---|---|
| 1 天 | 195 MiB |
| 1 周 | 1.3 GiB |
| 1 月 | 5.7 GiB |
| 3 月 | 17.1 GiB |
| **1 年** | **69.5 GiB** |

**开启默认轮换后不会**（事件 30 天 / 变更流 7 天 / 审计 365 天 / 幂等键 30 天 / 代理事件 30 天 / 已结束会话 365 天，结算与未结束会话永久保留）：

```
稳态行数 ≈ 14,870,880 行  →  稳态体积 ≈ 3.2 GiB
```

曲线形状：**前 30 天持续上涨**（事件层在攒），第 30 天起进入进出平衡——每天删掉的旧事件 ≈ 每天新增的事件，SQLite 的空闲页被后续写入复用，**体积封顶在约 3.2 GiB 不再增长**。

### 4.5 空间构成与优化记录

第一次压测时稳态是 **36.5 GiB**，两处结构性浪费：

| 问题 | 占比 | 处理 | 效果 |
|---|---|---|---|
| 每个事件都写一条 `audit_log` | 审计 1.05 亿行/年 | 事件不再写审计（`match_events` 本身即记录，见 [docs/03](03-数据模型.md) §5） | 日行数 −289k |
| `idempotency` 表永不清理 | 稳压 23.6% | 加 `IDEMPOTENCY_RETENTION_DAYS`（默认 30 天，远长于任何重试窗口） | 稳态 −370 MB |
| `idx_match_events_kind` / `idx_audit_target` 没有查询用它 | 约 5% | 删除 | 每行少一条索引项 |

**瓶颈不在吞吐**（2,221 ops/s vs 需求约 3–30 ops/s，余量两个数量级以上），**在保留策略**。调容量的旋钮是保留天数，不是线程数。

### 4.6 SQLite 的空间行为（必须知道的）

删除行**不会**把页还给操作系统，文件不会自动变小。这不是泄漏：

- 空闲页进入 freelist，后续写入优先复用它 → 体积在稳态值封顶。
- 想真正回收磁盘空间：停服后 `sqlite3 ccnr-data.db "VACUUM;"`（需要约 2 倍磁盘空间的临时空间）。

**不建议常开 `auto_vacuum`**：它在每次事务里搬页，直接抬升写放大，而稳态封顶已经解决了问题。

## 5. 排障

| 现象 | 原因与处理 |
|---|---|
| 启动报「数据库模式版本不匹配」 | 库文件是别的版本建的。**不要手改 `schema_meta`**；按 [docs/03](03-数据模型.md) §6 迁移 |
| 启动报「bind 端口已被占用」 | `--bind` 换端口，或先 `lsof -i :8081` |
| 启动报配置范围错 | 是刻意的：越界配置一律拒绝启动，不静默钳制 |
| `FAILED_PRECONDITION: request_id … 已被 … 以不同载荷使用` | 模组每次重试都新生成 `request_id`。见 [docs/04](04-对接说明.md) §2.4，键必须标识**一次意图** |
| 日志刷「订阅游标 N 早于变更流最早保留的 M」 | 订阅方落后超过 `CHANGE_RETENTION_DAYS`。订阅方需要重新做一次全量对账，或调大该保留天数 |
| 日志刷「结算前后端经验不一致」 | 模组本地账本与库不一致。查 `settlements WHERE diverged = 1`，以模组侧为准已经覆盖，但漂移原因要查 |
| `database is locked` | 有长事务占着写锁。检查是否有人手工 `sqlite3` 开着事务；`busy_timeout` 是 5 秒 |
| 磁盘涨到稳态值以上 | 保留天数被调大了，或某类写入量超预期。用 §4.5 的 `dbstat` 分解定位（`loadtest.py` 里就有这段查询） |
| 服务重启后模组大量重放 | 模组本地队列在补发，正常。幂等键保证不会重复落账 |
