# 04 · 对接说明

对接三方：**Gate 代理**（数据面）、**CCNR-RP 模组服务端**（权威端，本轮之后接）、**管理脚本 / 控制台**。

## 1. Gate 侧

### 1.1 打开 Gate API

```yaml
# gate 的 config.yml
api:
  enabled: true
  bind: localhost:8080      # 只监听内网/回环
```

启用后 Gate 暴露 `minekube.gate.v1.GateService`（`GetPlayer` / `ListPlayers` / `ListServers` / `ConnectPlayer` / `StoreCookie` / …）。

### 1.2 Python 客户端

```bash
uv add minekube-gate-grpc-python minekube-gate-protocolbuffers-python \
  --index https://buf.build/gen/python
```

```python
import grpc
from minekube.gate.v1 import gate_service_pb2 as gatepb
from minekube.gate.v1 import gate_service_pb2_grpc as gateapi

channel = grpc.insecure_channel("gate-host:8080")
stub = gateapi.GateServiceStub(channel)
for server in stub.ListServers(gatepb.ListServersRequest()).servers:
    print(server.name, server.address)
```

### 1.3 职责边界（重要）

| 谁做 | 什么 |
|---|---|
| Gate | 玩家连接、转服、命令执行、声音播放、Cookie 存取 |
| CCNR-Data | **只做数据**：存储、规则、审计、变更流 |

**本服务不直接调用 Gate**。原因：这会让数据服务依赖代理集群的可用性——代理重启时连"记一条结算"都失败，数据面与控制面的故障就耦合了。

需要联动时由**模组服务端**做中介（它本来就要连两边）：

```
事件发生 → 模组上报 CCNR-Data（RecordEvent）
         → 模组读返回 / 订阅变更流
         → 模组决定表现（播声音 / 转服 / 发命令）
```

声音 API 还有一个硬约束：**发射者与接收者必须在同一个后端服务器**，否则 Gate 返回 `ErrDifferentServers`。跨服播放要先转服。

### 1.4 多实例与健康检查

Gate 多实例用 Gate Connect（`connect.enabled: true` + 相同 `name`）做零配置负载均衡与故障转移，不需要外部 LB。

CCNR-Data 侧配合两点：

- 实现标准 gRPC 健康检查，K8s / HAProxy 可直接探活。
- 停机时先把健康状态置为 `NOT_SERVING` 再 drain（`server.ServerHandle.stop()` 已实现），负载均衡会先把流量挪走。

## 2. 模组端接入点

来源：对本仓库 `CCNR-RP` 只读审计得到的真实调用点（见下表 `文件:行`）。原则是**在每个"汇聚点"接一次**，而不是在每个上游分支各接一次。

### 2.1 结算 → `RecordSettlement`

**唯一汇聚点：`experience/ExperienceService.java:380` `settleUser(String, boolean)`。**

所有产生经验变化的路径都经过它：`/rp settle`（`command/XpCommand.java:68`）、`/rp settle all`（`:108`）、死亡与断联结算（`status/StatusManager.java:249`、`:568`）、疏散（`ExperienceService.java:487`）、退场。

在第 393 行 `users.save()` 之后、第 407 行 `return new SettleSummary(...)` 之前接：

```java
SettleSummary summary = new SettleSummary(gain, newXp, newLevel, changes);
dataSink.recordSettlement(playerUuid, matchId, reason, before, summary);  // 异步 + 本地队列
return summary;
```

`SettleSummary` 的字段正好一一对应 `RecordSettlementRequest`：

| 模组 | proto |
|---|---|
| `gain` | `gain` |
| `newXp`（= `xp_after`） | `xp_after` |
| `newLevel` | `level_after` |
| `before`（`:388` 的 `users.userXp`） | `xp_before` |
| `curve.level(before)` | `level_before` |
| `changes: List<XpChange>` | `lines: repeated SettlementLine` |
| — | `match_id`、`reason` 由模组补 |

`reason` 建议取值：`command` / `death` / `offline` / `evac` / `retire` / `round_end`。

### 2.2 事件 → `RecordEvent`

| 事件 | 接入点 | `kind` |
|---|---|---|
| 事件触发（三条触发路径的唯一汇聚点） | `event/EventManager.java:379` `startEvent(int)` | `CONFIG_EVENT_TRIGGERED` |
| 事件结束 | `EventManager.java:632` `endEvent(...)` | `EVENT_ENDED` |
| 清空事件 | `EventManager.java:200` `clearAll()` | `EVENTS_CLEARED` |
| 阶段推进（自动推进与手动 `setPhase` 都汇到 `broadcastMatchState`） | `EventManager.java:482` `setPhase` / `:292` `clock.tick` 分支 | `PHASE_ADVANCED` |
| 一局收束 | `EventManager.java:528` `end(String reason)` | `ROUND_ENDED` |
| 游戏结束 | `EventManager.java:651` `gameOver()` | `GAME_OVER` |
| 部署落位 | `character/CharacterService.java:206` `onDeployPosition` / `:262` `onKillDeploy` | `CHARACTER_DEPLOYED` |
| 阵亡 | `experience/ExperienceService.java:276` `emitDeath` | `CHARACTER_DEATH` |
| 击杀 | `ExperienceService.java:234` `emitKill` | `CHARACTER_KILL` |
| 疏散 | `ExperienceService.java:473` `evacuateAlive` | `EVACUATION` |
| 刷新波 | `spawn/SpawnFramework.java` `triggerWave` | `SPAWN_WAVE_TRIGGERED` |

**不要上报 `character_alive`**：它是每 60 秒对每个存活玩家的规则引擎内部广播（`ExperienceService.java:208` `emitAliveEvents`），属于规则计算，不是对局事件。上报它会让事件量直接翻几十倍。

注意 `/rp gameover`（`EventCommand.java:63`）**不会**结算也不会结束对局——它只播动画。所以 `GAME_OVER` 与 `ROUND_ENDED` 是两件事，都要接。

### 2.3 `match_id` 从哪来

模组目前没有对局标识，`EventManager` 的运行时状态（`clock.index`、`events` 状态、`running`、`runStart`）全部只在内存里，重启即丢。

推荐：`CCNRRPMod` 启动时生成一个 `match_id`（UUID），`EventManager.clearAll()`（也就是重开一局）时换一个新的，上报表里所有请求都带上它。这样即使模组重启导致状态丢失，数据侧仍能按 `match_id` 归组已上报的部分。

### 2.4 幂等键怎么生成

`request_id` 必须唯一标识**一次业务意图**，且重试时保持不变：

- 结算：`match_id + "/" + playerUuid + "/" + settledAtMillis`
- 事件：`match_id + "/" + kind + "/" + occurredAtMillis + "/" + definitionId`

**不要用随机 UUID 每次重试新生成**——那样重试就变成重复落账了。这正是幂等键存在的意义。

### 2.5 本地队列 + 重试

数据服务不可达时（模组侧判定：连接失败 / `UNAVAILABLE`），把请求写本地队列（模组已有的 `world/ccnr_rp/` 目录，与 `PendingNoticeStore` 同风格），按 `request_id` 重放。

- `UNAVAILABLE` / `INTERNAL` → 入队重试（可重试）
- `INVALID_ARGUMENT` / `FAILED_PRECONDITION` → **不重试**，记日志并丢弃（重试永远不会成功，只会堆队列）

### 2.6 依赖冲突

Minecraft 自带 Guava / Netty，与 gRPC-Java 冲突，必须 ShadowJar 重定位：

```gradle
shadowJar {
    relocate 'io.grpc', 'com.ccnrcom.rp.shaded.io.grpc'
    relocate 'com.google.protobuf', 'com.ccnrcom.rp.shaded.com.google.protobuf'
    relocate 'io.netty', 'com.ccnrcom.rp.shaded.io.netty'
    relocate 'com.google.common', 'com.ccnrcom.rp.shaded.com.google.common'
}
```

**gRPC 调用必须异步**，回调里 `server.execute(() -> ...)` 回到游戏主线程。绝不阻塞服务端 tick。

### 2.7 Java 桩怎么生成

`proto/moddata/v1/moddata.proto` 里已经写好：

```proto
option java_package = "com.ccnrcom.rp.data.grpc.v1";
option java_multiple_files = true;
```

用 `protoc` + `protoc-gen-grpc-java` 生成即可，字段名与本文档一致。

## 3. 等级显示迁移（本轮明确要求）

### 3.1 目标形态

```
模组服务端（权威：算等级）
   │ GetPlayer(server_id, player_uuid)  ← 每次需要显示时取
   ▼
CCNR-Data（只负责存和还）
   │
   ▼
模组服务端 → UserXpS2C / 档案包 → 客户端渲染
```

**规则（三条，缺一不可）**：

1. **模组服务端是权威端**：等级由它算、由它决定显示什么。
2. **模组服务端负责取数**：客户端不直连数据服务。
3. **取不到就不显示**：数据服务不可达时，客户端**不显示等级**，绝不回退本地推算（本地推算会得出与权威端不同的数字，比不显示更糟）。

### 3.2 现状：等级被算了三遍

审计发现同一个等级在三个地方各算一次，这是必须收敛的根源：

| 位置 | 现状 |
|---|---|
| `experience/LevelCurve.java:26` | 权威实现（`base` / `pow` 曲线） |
| `user/UserService.java:262` `level(uuid)` | **第二处独立计算**，每次调用都重建曲线 |
| `client/StatusHud.java:230` `levelProgress()` | **客户端第三处计算**（用服务端下发的 `levelBase`/`levelPow` 自己算） |

等级**没有**存在任何地方：`UserProfile`（`user/UserService.java:28`）没有 `level` 字段，数据库 `users` 表（`data/DbSchema.java:36`）也没有 `level` 列——全是现算的。
