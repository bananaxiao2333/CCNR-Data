# 03 · 数据模型

权威定义是 `src/ccnr_data/schema.sql`。本文解释**为什么不变量是这样、索引为什么只有这些**。

## 1. 时间表示

所有时间列都是 **UTC epoch 毫秒整数**（`INTEGER`）。理由：可排序、无时区歧义、SQLite 与 PostgreSQL 语义一致（PostgreSQL 侧对应 `BIGINT`，需要人类可读时用 `to_timestamp(col / 1000.0)`）。

## 2. 表清单

| 表 | 角色 | 轮换 |
|---|---|---|
| `schema_meta` | 模式版本（单行，`id=1`） | — |
| `players` | 玩家档案：经验 / **等级** / 名字 / 版本号，主键 `(player_uuid, server_id)` | 永不 |
| `role_overrides` | 角色开关，主键 `(player_uuid, server_id, role)`，**保留 `enabled=0` 的行** | 永不 |
| `server_configs` | 服务器策略（`role_policy` / `config_json`），主键 `server_id` | 永不 |
| `settlements` | 结算头，`request_id UNIQUE` | 永不（业务记录） |
| `settlement_lines` | 结算明细，外键级联 | 永不 |
| `match_events` | 事件流水，只追加 | 30 天 |
| `idempotency` | 幂等键 + 缓存响应 | 30 天 |
| `audit_log` | 状态变更审计（前后值） | 365 天 |
| `change_log` | 变更流，`seq` 全局单调 | 7 天 |

### 为什么 `role_overrides` 保留 `enabled=0`

"从没给过这个角色"和"给过又收回"是两件不同的事：前者回退到配置默认，后者必须继续压制默认。删行会把后者错误地变成前者。

### 为什么等级是**存**的而不是从经验算的

等级曲线属于游戏逻辑（`level.base` / `level.pow` 是模组的 serverconfig）。曲线改了，历史数据用哪套曲线算？没有正确答案。

因此本服务把等级当作**权威端上报的观测值**存下来：模组算什么就是什么。好处是历史可追溯、改曲线不改历史；代价是模组必须显式上报等级（`ApplyExperienceRequest.level`、`RecordSettlementRequest.level_*`）。

## 3. 事务与不变量

### 3.1 幂等行与业务行同事务

```
BEGIN IMMEDIATE
  INSERT INTO idempotency(...) ON CONFLICT DO NOTHING   -- 认领
  业务写入
  UPDATE idempotency SET response_json = ...
COMMIT
```

因此：**幂等行存在 ⟺ 业务已生效**。不存在"认领了但没执行"或"执行了但没记录"的中间态。

`BEGIN IMMEDIATE` 而不是 `BEGIN`：立刻取写锁，让并发写在这里排队（`busy_timeout` 内等待），而不是在 COMMIT 时才发现冲突要回滚重试。

### 3.2 结算的一致性约束（服务端强制）

| 约束 | 违反时 |
|---|---|
| `gain == xp_after - xp_before` | `INVALID_ARGUMENT` |
| 有明细时 `Σ lines.value == gain` | `INVALID_ARGUMENT` |
| 无明细时 `gain == 0` | `INVALID_ARGUMENT` |
| `xp_*` / `level_*` 非负 | `INVALID_ARGUMENT` |

前两条对应模组 `SettleSummary` 的既有保证（`gain = XpChangeList.sum(changes)`），在这里再挡一次是为了在边界上发现模组侧的 bug，而不是把脏数据存进历史。

### 3.3 经验漂移

库里的 `experience` 与上报的 `xp_before` 不一致时：**以权威端为准覆盖**，同时把 `xp_diverged=true` 与 `stored_xp_before` 回报给模组，并打一条 WARN 日志。

不选"以库为准"是因为模组才是权威端；不静默覆盖是因为本地账本漂移了必须让人知道。

### 3.4 角色变更也推进 `players.version`

`version` 表达"这个玩家聚合被写过几次"。角色是聚合的一部分，所以 `SetRoleOverride` 也会 upsert `players` 行（保留原经验/等级）并 `+1`。

## 4. 索引：只留真的有查询用的

每条索引都会摊到**每一次写入**上。实测（40,000 事件、15 项索引）里索引占 `match_events` 空间的约 55%，所以索引不是免费的。

| 索引 | 支撑什么 | 保留 |
|---|---|---|
| `players` PK `(player_uuid, server_id)` | 主键查找（`GetPlayer`） | ✅ |
| `idx_players_server` | 按服统计/运维查询 | ✅ |
| `role_overrides` PK | 主键 upsert | ✅ |
| `idx_role_overrides_player` | 取某玩家全部角色（`GetPlayer` 每次都要） | ✅ |
| `settlements.request_id UNIQUE` | 幂等重放判定 | ✅ |
| `idx_settlements_player` | 按玩家查历史 | ✅ |
| `idx_settlements_match` | 按对局查历史（**主要分析入口**） | ✅ |
| `idx_match_events_match(server_id, match_id, id)` | 按对局回放事件 | ✅ |
| `idx_match_events_occurred` | 轮换整批删除 | ✅ |
| `change_log` PK `seq` + `idx_change_log_server` | `WatchChanges` 游标与服务器过滤 | ✅ |
| `idx_change_log_occurred` | 轮换整批删除 | ✅ |
| `idx_audit_created` | 轮换整批删除 | ✅ |
| ~~`idx_match_events_kind`~~ | 没有查询用它 | ❌ **已删** |
| ~~`idx_audit_target`~~ | 没有查询用它 | ❌ **已删** |

**新增索引前先回答**：哪条查询会走它？如果答不上来，就是给每次写入加税。

## 5. 事件**不写审计行**（实测后的决定）

第一版给每个事件也写了一条 `audit_log`。压测显示这让审计成了最大的表之一：一天 28.8 万事件 → 一年 **1.05 亿行**，稳态体积从 3.2 GiB 涨到 36.5 GiB。

删掉的依据：`match_events` 本身就是那条不可变记录——谁（`actor_uuid`）、对谁（`target_uuid`）、何时（`occurred_at`）、何事（`kind` + `phase_id` + `definition_id`）、载荷（`payload_json`）全在，还有 `request_id` 可溯源。再落一条 audit 只是把同一件事写两遍。

`audit_log` 的职责收敛为：**状态变更的前后值**——经验、结算、角色、服务器策略。这四类写入量小、变更语义强，才是需要"改动前是什么、改成什么、谁改的"的地方。

## 6. 迁移

当前 `SCHEMA_VERSION = 1`。

**启动时版本校验**：库内版本 ≠ 程序版本 → `INTERNAL` 拒绝启动，并提示先备份、按本节处理。本服务**绝不自动改库**。

`bootstrap` 每次启动都会执行一遍 `schema.sql`（全部 `IF NOT EXISTS`），因此加**表**或加**索引**是安全的；但加**列**不行——`CREATE TABLE IF NOT EXISTS` 对已存在的表不会补列。

加列的正确流程：

1. `ALTER TABLE ... ADD COLUMN` 写成迁移脚本（`scripts/migrate_v1_to_v2.sql`）。
2. 备份：`sqlite3 ccnr-data.db ".backup ccnr-data.db.bak"`。
3. 停服 → 跑迁移 → 把 `schema.sql` 与 `SCHEMA_VERSION` 一起提到 2。
4. 启动，门禁里的 `test_server.py` 会验证 bootstrap 幂等。

> 迁 PostgreSQL 时：`INTEGER PRIMARY KEY AUTOINCREMENT` → `BIGINT GENERATED ALWAYS AS IDENTITY`；
> `INSERT ... ON CONFLICT DO NOTHING/UPDATE` 语法两边一致；
> `PRAGMA` 全部换成连接参数（`journal_mode` / `foreign_keys` 无对应物，靠服务端配置）。
> 这些差异会集中在 `db.py` 与 `schema.sql` 两处，`repo.py` 的 SQL 是可移植的。
