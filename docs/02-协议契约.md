# 02 · 协议契约

契约唯一权威是 `proto/moddata/v1/moddata.proto`。本文解释它的规则、语义与**与方案草图的差异**。

## 1. 字段编号规则

- 字段编号一经发布**永不复用**；删除字段必须同时 `reserved` 编号与名字。
- 不修改已有字段的类型与语义。新功能只**加字段、加方法**。
- 枚举 0 值必须是 `*_UNSPECIFIED`。
- 破坏性变更开新包（`moddata.v2`），服务端 v1/v2 同时注册。

旧版模组读到新增字段会自动忽略（proto3 未知字段保留）；新版模组靠 `PlayerData.version` 之类的版本号判断服务端是否支持某能力。

## 2. 服务与 RPC

`moddata.v1.ModDataService`：

| RPC | 类型 | 幂等 | 说明 |
|---|---|---|---|
| `GetPlayer` | unary | 读 | 取玩家档案（经验/等级/角色）。档案不存在 → `NOT_FOUND`（不隐式创建） |
| `ApplyExperience` | unary | 是 | 按增量改经验，等级可选。玩家不存在则**创建**（首次加经验必须能成） |
| `RecordSettlement` | unary | 是 | 上报一次结算的完整结果 + 逐条明细 |
| `RecordEvent` | unary | 是 | 上报一个对局事件节点。返回的 `seq` 就是 `WatchChanges` 游标 |
| `SetRoleOverride` | unary | 是 | 角色开关（含显式禁用，保留禁用记录） |
| `GetServerConfig` | unary | 读 | 读服务器策略。无记录 → 默认 `ROLE_POLICY_OPEN`，且**不设置** `updated_at` |
| `UpdateServerConfig` | unary | 是 | 部分更新服务器策略（`optional` 字段表达"这项不改"） |
| `WatchChanges` | server streaming | — | 变更流，`since_seq` 断线续传 |

健康检查：标准 gRPC Health Checking Protocol（`grpc.health.v1.Health`），同时注册 `""` 与 `moddata.v1.ModDataService`。

## 3. 幂等语义

- 幂等键是 `request_id`，作用域是**单方法**：同一个 `request_id` 用在不同 RPC 上 → `FAILED_PRECONDITION`。
- 指纹覆盖请求的**业务意图**（键排序后的紧凑 JSON 的 sha256）。
  - 未提供的时间戳按原始值（0）参与指纹，**不是**服务端补的 `now()`——否则同一请求重放会被误判成"同键不同载荷"。
  - 服务端补的默认值（如 `reason` 缺省为 `unspecified`）才参与指纹，因为它是确定性的。
- 命中已有键且载荷一致 → 返回**缓存的原响应**（`json_format.Parse` 回放，`ignore_unknown_fields=True`）。
- 命中已有键但载荷不同 → `FAILED_PRECONDITION`。宁可报错，也不回放一个语义不同的结果。

## 4. 错误码

| 码 | 何时 |
|---|---|
| `INVALID_ARGUMENT` | 入参校验失败（见 §6）、语义不合法（`gain ≠ xp_after - xp_before`、明细合计 ≠ gain、`PHASE_ADVANCED` 缺 `phase_id`） |
| `NOT_FOUND` | `GetPlayer` 查不到档案 |
| `PERMISSION_DENIED` | 角色策略为 `FROZEN` 时的 `SetRoleOverride` |
| `FAILED_PRECONDITION` | 幂等键被复用但载荷不同 |
| `INTERNAL` | 数据库错误、模式版本不符、未预期异常（消息不外泄内部细节，日志里有完整栈） |

翻译点只有一个：`service.ModDataService._handle`。**不要在 RPC 里直接 `context.abort`**。

## 5. 与方案草图的差异（都是刻意的）

| 草图 | v1 实际 | 理由 |
|---|---|---|
| `PlayerData` 字段 `player_uuid=1, experience=2, roles=3, flags=4, version=5, updated_at=6, level=7` | 重新编号，并加 `server_id`、`username` | v1 是新契约，没有已发布的兼容包袱；草图的编号是为了演示"新字段用新编号"这条规则本身 |
| `flags` map | **删除** | 没有任何写入方，永远是空的占位字段。等真有写入口再加（加字段是兼容变更） |
| `force_role_enabled` + `force_role_disabled` 两个布尔量 | 单枚举 `RolePolicy{OPEN, FROZEN, FORCED_ON}` | 两个布尔量可以同时为真，是**无法表达**的矛盾态。收敛成枚举后非法状态不可构造 |
| 只有 `GetConfig` | 加 `UpdateServerConfig` | 否则 `RolePolicy` 永远写不进去，`FROZEN` 分支是死代码 |
| `WatchChangesRequest.since_version` | `since_seq` | 它是 `change_log.seq`（全局单调的变更游标），不是实体版本号。名字不同才不会用错 |
| `ChangeEvent.event_type` 字符串 | `change_type` 字符串（保留）+ `RecordEventRequest.kind` 枚举 | 变更流类型有限且固定用字符串便于扩展；事件种类要挡住垃圾值，用枚举 |
| `ApplyExperience` 里挡 `force_role_disabled` | 改为在 `SetRoleOverride` 上挡 | 经验与角色是两件事，用角色策略挡加经验在语义上是错的 |
| 未提 `RecordEvent` / `RecordSettlement` | v1 的核心 | 需求是"事件、结算全都发给数据服务器"，这是本服务存在的理由 |
| `SettlementLine.line_no` | 删除 | `repeated` 的顺序本身就是上报顺序，再传一个行号是冗余且要额外校验一致性 |

## 6. 入参校验（信任边界）

调用方在主机边界之外（模组服务端 / Gate 插件 / 管理脚本），**所有入参先过 `validation.py`**：

| 项 | 规则 | 上限 |
|---|---|---|
| `player_uuid` / `actor_uuid` / `target_uuid` | 合法 UUID，规范化为小写带连字符 | 64 |
| `server_id` / `role` / `match_id` / `phase_id` / `definition_id` | `[A-Za-z0-9][A-Za-z0-9_.:-]*`，可空的场景见 proto 注释 | 64（match_id 128） |
| `request_id` | 同上字符集 | 128 |
| `reason` / `source` / `actor` / `username` | 普通文本，去空白 | 128 / 64 |
| `rule_id` / `title` | **自由文本**（可能是中文，模组会把标题拼进 rule id） | 256 |
| `payload_json` / `config_json` | 合法 JSON **对象**，键排序后紧凑存储 | 64 KiB |
| 时间戳 | 未设置（整零）→ 取当前；否则须落在 `[2020-01-01, now+24h]` | — |
| `level` / `xp_*` | 非负 | — |
| 结算明细条数 | — | 512 |

长度上限不是安全边界，是**用量边界**：防止一次请求塞爆事务或撑爆一行。

## 7. 兼容性检查清单

改 proto 前逐条确认：

1. 只加字段/加 RPC？还是删/改？
2. 删字段 → `reserved` 编号和名字了吗？
3. 枚举 0 值还是 `*_UNSPECIFIED` 吗？
4. `uv run python scripts/gen_proto.py` 跑了吗？（门禁第 6 关会查）
5. 旧版模组的请求形状还能被正确解析吗？加一条回归测试。
