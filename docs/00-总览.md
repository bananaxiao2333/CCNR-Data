# 00 · 总览

## 1. 本服务在整套系统里的位置

```
玩家客户端（任意 MC 版本）
        │
        ▼
Gate 代理集群（Go，约 10MB/实例）        ── 数据面：连接 / 转服 / 命令 / 声音
        │  gRPC
        ▼
┌──────────────────────────────────────┐
│  CCNR-Data（本仓库，Python + gRPC）   │  ── 控制面：存储 / 规则 / 审计
│   ModDataService                     │
└──────────────┬───────────────────────┘
               │ SQL
               ▼
        SQLite（默认） / PostgreSQL（后续）
               ▲
               │ gRPC（权威端上报）
        ┌──────┴───────────────────────┐
        │ CCNR-RP 模组服务端（Forge）   │  ── 游戏逻辑 + 权威数值
        └──────────────────────────────┘
```

## 2. 角色分工（谁说了算）

| 问题 | 谁负责 | 说明 |
|---|---|---|
| 经验数值是多少 | **模组服务端** | 权威端。经验规则引擎（`ExperienceRule`）在模组里跑 |
| 等级是多少 | **模组服务端** | 权威端按 `level.base` / `level.pow` 曲线算好，随请求上报 |
| 经验/等级**存哪** | **本服务** | 原样落库，不重算、不猜 |
| 角色开关 | 本服务存，受服务器策略约束 | `RolePolicy` 可冻结或强制 |
| 事件与结算的**历史** | **本服务** | 只追加，永不改写 |
| 玩家连哪个后端 | Gate | 本服务不管连接 |

**本服务不做的事**：不算等级曲线、不跑经验规则、不做游戏表现（声音/动画/转服由 Gate 与模组负责）。

这条边界是刻意的：等级曲线一旦在两处实现，就一定会出现"模组显示 4 级、面板显示 3 级"这类问题。

## 3. 它承接的四类写入

| 写入 | 来源（模组端代码） | 频率量级 |
|---|---|---|
| **事件** `RecordEvent` | `EventManager` 的生命周期节点：阶段推进 / 事件触发与结束 / 结局 / 游戏结束 / 阵亡 / 击杀 / 部署 / 疏散 / 刷新波 | 最高（决定容量） |
| **结算** `RecordSettlement` | `ExperienceService.settleUser()` —— `/rp settle`、死亡、断联、`/rp evac`、退场 | 低（每局每人数次） |
| **经验增量** `ApplyExperience` | `/rp xp add` 这类零星改动 | 很低 |
| **角色 / 策略** `SetRoleOverride` `UpdateServerConfig` | 管理命令 / 事件剧本 / 控制台 | 极低 |
| **读档** `GetPlayer` | 游戏内等级显示取数 | 高（读，无写放大） |

## 4. 三条贯穿全局的设计约束

1. **幂等**：所有写入 RPC 都带 `request_id`。幂等行与业务行**同事务提交**，因此"幂等行存在"就等于"业务已生效"；重放原样回放缓存响应，复用键配不同载荷直接报错。
2. **审计 + 变更流**：状态变更（经验/结算/角色/策略）同时落 `audit_log`（前后值、谁改的）与 `change_log`（推送游标）。事件不另写审计——`match_events` 本身就是那条不可变记录（见 [docs/03](03-数据模型.md) §5）。
3. **日志轮换**：`match_events` / `change_log` / `audit_log` / `idempotency` 都按天清理，业务表（`players` / `settlements` / …）永不自动清除。没有轮换，容量会在一年内涨到 70 GiB；有轮换，封顶在约 3.2 GiB（见 [docs/05](05-部署与运维.md) §4）。
